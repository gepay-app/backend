# §3 — HTTP & API layer

## Routing & controllers

- Base path: `/api/v1` (`@RequestMapping("/api/v1/...")`). Resources are plural
  nouns (`/identities`, `/payments`, `/webhooks`).
- Controllers are `@RestController` in `<module>.internal.delivery.http`, thin:
  validate input, map request → command/DTO, call the `api` facade, wrap the
  result in `ApiResponse`. No business logic in controllers.
- Request bodies are `record`s in `internal/delivery/http/req` with
  `jakarta.validation` constraints (`@NotBlank`, `@Email`, `@NotNull`, `@Size`).
- Responses are `record`s in `internal/delivery/http/res` (suffix `Res`, mapped
  via a `static from(...)` factory). `api/dtos` are the service/cross-module
  contract and must **not** be serialized to the wire — see §2.5.
- Method-level authorization via `@PreAuthorize("hasRole('SUPER_ADMIN')")`
  (method security enabled in `identity`'s `SecurityConfig`).

## Response envelope (success)

```java
ApiResponse<T>(String message, T data)
```

- `message` is a localized success message (often `common.success` via
  `MessageHelper`); `data` is the payload or `null`. Null fields are omitted.

## Status codes

- Use `ResponseEntity.status(...)` explicitly; match semantics, not convenience.
- `200` for reads and in-place mutations, `201` for creation where a new
  resource identity is returned, `204` for no-content deletes. Errors follow the
  `GlobalExceptionHandler` mapping (see §6).

## Validation

- Bean validation on request records produces per-field `errors` in the
  `ErrorResponse` (400). Service-layer field problems use `ValidationException`.
- Reuse the shared constraint messages (`jakarta.validation.constraints.*`)
  already localized in the app-wide bundle.

## Pagination

Lists are **keyset/cursor-based** — never offset, never `COUNT`. At the target
scale (tens–hundreds of millions of rows) `COUNT(*)` and `OFFSET n` (O(n)) are
both non-starters; keyset keeps each page at O(limit) via an index range scan.

- Envelope: `CursorPage<T>` (`platform.web.response`):
  `{ items, hasNext, nextCursor }`. `nextCursor` is `null` on the last page.
- Controller params: `?cursor=<UUID>&size=<n>` — `cursor` omitted on the first
  request; `size` default `20`, capped at `100` in the service.
- Repository keyside: order by `id DESC` (UUID v7 is time-ordered) and use
  `Limit` (not `Pageable`):

  ```java
  List<Payment> findByUserIdOrderByIdDesc(UUID userId, Limit limit);
  List<Payment> findByUserIdAndIdLessThanOrderByIdDesc(UUID userId, UUID cursor, Limit limit);
  ```

  Query `size + 1` rows; `CursorPage.of(rows, size, e -> e.getId().toString())`
  trims the extra row and derives `hasNext`/`nextCursor`. Map to the HTTP `Res`
  with `CursorPage.map(...)`.
- Requires an index on `(owner_column, id DESC)`; add the filter column before
  `id` when a filtered list is added (e.g. `(user_id, status, id DESC)`).

## OpenAPI (springdoc)

- Spec + Swagger UI are generated by `springdoc-openapi-starter-webmvc-ui`:
  `GET /v3/api-docs` (JSON) or `/v3/api-docs.yaml`; UI at `/swagger-ui.html`.
  Both paths are `permitAll` in `SecurityConfig` (dev/frontend tooling).
- Global metadata + the `bearerAuth` (HTTP bearer / Firebase ID token) scheme live
  in `platform/config/OpenApiConfig`.
- Annotate controllers so the frontend can read intent:
  `@Tag` per controller, `@Operation(summary = "...")` per handler, and
  `@SecurityRequirement(name = "bearerAuth")` on protected controllers/handlers
  (omit on public ones so they show as unauthenticated).
- `OpenApiDocsTest` guards that the spec still serves and keeps the expected
  paths + security scheme.
